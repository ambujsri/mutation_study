# Coding Guidelines — Medvolt Protein Engineering

**Applies to:** all Python code, configuration and data artifacts in this repository.
**Standard:** written to the bar expected of computational R&D in large regulated
pharmaceutical organizations, where results may feed decisions on which molecules
are synthesized and tested, and where any number must be traceable back to the
code, data and settings that produced it.

The key words **MUST**, **MUST NOT**, **SHOULD** and **MAY** are used as in RFC 2119.

---

## 1. Principles

1. **Reproducible:** the same commit, config and raw data MUST produce byte-identical
   artifacts.
2. **Traceable:** every output MUST be attributable to a config file, a code version
   and its input data.
3. **Explicit over implicit:** no hidden defaults, no magic numbers, no silent data
   changes.
4. **Fail fast and loudly:** invalid input stops the pipeline with a clear message; it
   is never "worked around" silently.
5. **Scientifically honest:** validation MUST reflect how the model will be used
   (e.g. unseen protein families), not the most flattering split.
6. **Readable first:** code is read far more often than it is written, often by a
   reviewer or auditor who did not write it.

---

## 2. Repository structure

```text
config/config.yaml        Run configuration: setup and decisions only (section 4)
src/common/constants.py   Fixed dataset facts and conventions (section 4)
src/common/config.py      Config loading, validation, path resolution, logging
src/<stage>.py            One module per pipeline stage (preprocess, validation, train, predict)
data/raw/                 Immutable inputs, never written to by code
data/processed/           Derived tables, always regenerated by code
outputs/                  models/, figures/, reports/; regenerated, never hand-edited
tests/                    pytest suite mirroring src/
docs/                     Design notes and these guidelines
main.py                   Single entry point that orchestrates the stages
```

- Each pipeline stage MUST be runnable on its own (`python -m src.<stage>`) and via `main.py`.
- Code shared by two or more stages MUST live in `src/common/`, not be copied.
- Stages exchange data through files in `data/processed/` and `outputs/`, not hidden
  in-memory state, so any stage can be re-run independently.

---

## 3. Python style

| Topic | Rule |
|---|---|
| Version | Python ≥ 3.10. Use `from __future__ import annotations`. |
| Formatter | `ruff format` (Black-compatible), line length 110. Not negotiable in review. |
| Linter | `ruff check` with the rule set in `pyproject.toml`; zero warnings on merge. |
| Types | Every public function MUST have full type hints. `mypy src/` MUST pass. |
| Imports | Standard library, third-party, first-party, separated by blank lines (ruff `I`). No wildcard imports. Absolute imports from `src.` only. |
| Naming | `snake_case` functions/variables, `PascalCase` classes, `UPPER_SNAKE_CASE` constants. Constants module imported as `from src.common import constants as const`. |
| Functions | Do one thing; aim for < 50 lines. Pure where possible (input → output, no global mutation). Return new DataFrames rather than mutating arguments. |
| Paths | `pathlib.Path`, never string concatenation. All paths resolved via `src.common.config.resolve_path`. |
| Dead code | No commented-out code, no unused functions; version control is the archive. |

---

## 4. Configuration vs. constants (the decision rule)

Every literal value in the codebase belongs in exactly one of three places.

| Put it in… | When the value… | Examples |
|---|---|---|
| **`config/config.yaml`** | sets up the environment, or is a scientific / modelling **decision** a reviewer could question or a user could change between runs | random seed, directory and file names, encoding choice, imputation strategy, CV strategy and folds, hyperparameters, ranking weights, top-k, log level |
| **`src/common/constants.py`** | is a **fixed fact** about the data or a code convention; changing it means the data or the code changed, not the experiment | column names, embedding prefix and dimension, H/E/C codes, documented value ranges, expected table sizes, engineered-column naming, allowed enum choices, log format |
| **Inline in code** | is intrinsic to the algorithm and has no meaning outside it | `0` and `1` as indices, `axis=1`, `index=False` |

Rules:

- Config MUST NOT contain column names or dataset schema. If the data provider renames a
  column, exactly one line in `constants.py` changes.
- Constants MUST NOT contain anything an experiment might tune. If you ask "should this
  be a CLI flag?", it belongs in config.
- Every closed-set config value (e.g. `onehot | ordinal`) MUST have a matching `Enum`
  in `constants.py` and be validated in `src/common/config.py` at load time.
- Constants MUST be immutable: `Final` annotations, `tuple` rather than `list`,
  `MappingProxyType` rather than `dict`.
- Every config value MUST carry an inline comment giving its unit, allowed values or
  rationale.
- Code MUST NOT supply a fallback default for a config key (`cfg.get("x", 5)`); a
  missing key is a config error and must fail validation.

---

## 5. Documentation

- Every module starts with a docstring that says what it does and how it is run.
- Every public function and class has a **Google-style** docstring with `Args`,
  `Returns` and `Raises` sections whenever these are not obvious from the signature.
- Docstrings explain **why** (scientific rationale, leakage concerns, chosen
  trade-offs); code shows **what**. Comments that restate the code are removed in review.
- Non-obvious scientific choices (e.g. "imputation statistics fit on training data only")
  MUST be documented where the choice is made.
- `README.md` MUST always allow a new team member to set up and run the pipeline from a
  clean checkout.

---

## 6. Logging and error handling

**Logging**

- Use `logging.getLogger(__name__)` in each module. `print()` is not allowed in `src/`.
- `INFO`: stage milestones, table shapes, check results. `WARNING`: anomalies that were
  handled or tolerated. `ERROR`: just before raising. `DEBUG`: detail for local diagnosis.
- Use lazy formatting (`logger.info("rows=%d", n)`), not f-strings, inside log calls.
- Log every data-altering action (rows dropped, values imputed) together with its counts.
- MUST NOT log secrets, credentials or personal / patient-identifiable data.

**Errors**

- Validate inputs at the boundary (file load, config load, merge) and raise immediately.
- Raise specific exceptions (`ValueError`, `FileNotFoundError`, or a project exception
  such as `ConfigError`) with a message saying what was expected, what was found and
  where.
- Bare `except:` and `except Exception: pass` are not allowed. Catch only what you can
  handle.
- Behaviours that can be tolerated (e.g. row loss in a merge) are governed by explicit
  `fail_on_*` flags in config, never decided ad hoc in code.

---

## 7. Data handling and scientific integrity

- `data/raw/` is **read-only**. Code MUST NOT write, rename or "fix" raw files.
- **No silent data changes.** Every imputation, drop or clip is driven by config, logged,
  and recorded in the processed-data manifest.
- **Targets are never imputed.** Rows with missing labels are dropped and counted.
- **No leakage.** Any fitted transform (scaler, PCA, imputer, encoder with learned
  state) MUST be fit inside each training fold only and applied to the held-out fold
  and to candidates.
- **Grouped validation.** When rows share a protein or family, random K-fold is an
  optimistic reference only. The primary estimate MUST use group-aware splits that
  match the deployment scenario.
- **Merges are verified:** cardinality (`validate="many_to_one"`), zero row loss and
  value alignment are asserted, not assumed.
- Out-of-distribution inputs (e.g. unseen families) MUST be flagged in outputs, not
  silently scored like everything else.
- Processed artifacts MUST be accompanied by a manifest (feature lists, seed,
  data-quality report) so downstream stages never re-derive column logic.

---

## 8. Reproducibility

- A single seed from `config.project.random_seed` is passed explicitly to every
  stochastic component (`random_state=`, `np.random.default_rng(seed)`). Global
  `np.random.seed()` is not allowed.
- Runtime dependencies and tooling are pinned exactly in `requirements.txt`.
  Dependency upgrades are their own reviewed change.
- Columnar outputs prefer Parquet (types preserved, deterministic). CSV is for
  human-facing reports.
- Model artifacts are saved together with the config used to produce them and the
  feature list they expect.
- Refactors that should not change behaviour MUST be shown to produce identical
  artifacts (e.g. `pandas.testing.assert_frame_equal` against a pre-change snapshot).

---

## 9. Testing

- Framework: `pytest`; tests live in `tests/` and mirror `src/` (`tests/test_preprocess.py`).
- Each public function has at least one unit test; each pipeline stage has a smoke test
  on a small synthetic fixture.
- Tests MUST cover the data contracts: schema violations, duplicate IDs, merge row loss,
  unknown categorical codes, NaN/inf handling and invalid config values.
- Tests are deterministic, independent of execution order, and MUST NOT read from or
  write to `data/` or `outputs/` (use `tmp_path`).
- Target ≥ 80 % line coverage on `src/`; 100 % on `src/common/`.

---

## 10. Version control and review

- Never commit directly to `main`. Branch as `feature/<topic>`, `fix/<topic>` or
  `chore/<topic>`.
- Commit messages follow Conventional Commits: `feat(preprocess): add relative position feature`.
- Do not commit data outputs, model binaries, notebooks with outputs, or secrets
  (enforced by `.gitignore`).
- Every change is reviewed by at least one other person. The reviewer checks the
  checklist in section 12, not just whether the code runs.
- CI MUST run `ruff check`, `ruff format --check`, `mypy src/` and `pytest` and block
  the merge on failure.

---

## 11. Security and compliance

- No credentials, tokens or connection strings in code or config. Use environment
  variables or a secrets manager.
- Use `yaml.safe_load`, never `yaml.load`. Never `pickle.load` / `joblib.load` an
  artifact from an untrusted source.
- This dataset is synthetic. Any future work with proprietary sequences or human-derived
  data MUST follow the organization's data-classification and privacy policies before
  any code touches it.
- Where outputs may support regulated decisions, follow ALCOA+ data-integrity
  principles (attributable, legible, contemporaneous, original, accurate; complete,
  consistent, enduring, available). In this codebase that means: logs, manifests,
  immutable raw data and versioned config.

---

## 12. Pre-merge checklist

- [ ] `ruff check .`, `ruff format --check .` and `mypy src/` pass.
- [ ] `pytest` passes; new behaviour has tests.
- [ ] No new literal values: each one is in `config.yaml` (decision) or `constants.py` (fact).
- [ ] New closed-set config options have an `Enum` and load-time validation.
- [ ] Public functions have type hints and Google-style docstrings.
- [ ] Data-altering steps are logged and recorded in the manifest.
- [ ] No fitted transform sees validation-fold or candidate data.
- [ ] Seed passed explicitly to every stochastic call.
- [ ] Refactors produce identical artifacts (evidence included in the PR).
- [ ] README and these guidelines are updated if behaviour or structure changed.
